# moyami 초기 공개 구현 기록

## 반영 범위

- 첫 방문에 계정 화면을 표시합니다. 최초 관리자는 배포자가 생성한 `BOOTSTRAP_KEY`로 가입하고, 이후에는 아이디·비밀번호로 로그인합니다.
- 최초 관리자 생성과 초대 키 소비는 Redis Lua 트랜잭션으로 처리합니다. 동시에 요청해도 관리자가 둘 생기거나 같은 키로 두 번 가입하지 않습니다.
- 초대 키는 관리자만 발급하며 24시간·1회 사용입니다. 발급 직후 취소할 수 있습니다.
- 비밀번호 scrypt 해시, 해시로 저장한 세션 토큰, HttpOnly 쿠키, 로그아웃 시 세션 폐기, 인증 시도 제한, JSON·Origin 검사를 적용했습니다.
- Vercel에서는 Upstash REST API를 이용하고, 로컬 단일 프로세스에서는 `data/auth.json`에 계정을 저장합니다. 파일은 임시 파일 작성 후 rename으로 교체합니다.
- 브라우저 localStorage와 IndexedDB는 계정 ID로 구분합니다. 다른 탭의 로그인·로그아웃도 반영합니다. 계정별 텍스트 기록 동기화는 아래 후속 구현에 추가했습니다.
- 기본 확장 저장소와 기본 소스 선택을 제거했습니다. 빈 서재에서 저장소 주소를 추가하도록 안내합니다.
- 표시 이름·프로젝트 이름·주소는 배포자가 정합니다. 연결 확장 패키지도 해당 앱 주소에 맞춰 빌드합니다.
- 키 생성 도우미 → Vercel Deploy Button → Upstash 연결 → 첫 가입 순서로 안내합니다. 생성한 키 값은 배포 링크에 포함되지 않습니다.
- GitHub 공개본에는 기존 개인 배포 이력, 토큰, `.state`, 실험 기록을 옮기지 않았습니다. Moya UI와 의존성의 라이선스는 유지합니다.

## 검증

- 실제 Redis를 포함한 서버 테스트 41개 통과.
- 실제 서버와 모바일 Chromium으로 관리자 가입, 초대 가입, 로그아웃, 탭 간 로그아웃, 계정별 저장 격리, 빈 저장소, 배포 키 도우미 확인.
- 기존 리더·소스 UI 브라우저 회귀 47개. 기본 저장소 자동 삽입에 의존하던 테스트는 저장소를 명시적으로 등록하도록 변경했고, 설정창 닫힘의 포커스 복원이 끝난 뒤 키보드 단축키를 검사하도록 수정했습니다.
- Chromium 연결 확장 회귀와 PWA 설치·오프라인 셸·업데이트 회귀 통과.
- 새 폴더에서 npm ci 및 Vercel CLI build 통과. Node.js 22 함수 출력 약 5.9MB, 정적 출력 약 2.7MB. 빌드 검증에만 쓴 빈 Vercel 프로젝트는 삭제했습니다.
- GitHub Actions에서 Redis·빌드·가입·리더·PWA 테스트를 자동 실행합니다.

## 배포 검증의 경계

이번 작업은 공개 저장소, 키 생성 페이지, 배포 구성과 Vercel 빌드를 검증했습니다. 새 사용자의 GitHub/Vercel 가입, Upstash 약관 동의 및 플랜 선택까지 대행한 것은 아닙니다. 배포 버튼을 누른 계정 소유자가 해당 절차를 완료해야 합니다. 기존 서비스 운영 배포는 변경하지 않았습니다.

원본 사이트의 인증·IP 차단, iOS/Android 연결 확장 배포 서명 조건은 기존과 같습니다. 이메일로 비밀번호를 복구하는 기능은 포함되지 않습니다.

## 경량 동기화 및 쉬운 배포 안내

- README 첫머리에 Moya Reader 웹·프로젝트 링크를 추가했습니다. 저장 공간이 필요한 이유와 Vercel 버튼 순서를 안내하고, 환경변수 이름은 접힌 고급 설명으로 옮겼습니다. 앱의 설정 누락 화면과 배포 도우미도 같은 용어를 사용합니다.
- `/api/sync`는 로그인 세션에서 계정 ID를 얻습니다. 요청에서 다른 사용자 ID를 지정해도 그 사용자의 데이터를 읽거나 쓸 수 없습니다.
- 저장소, 고정 소스, 작품별 최근 읽기, 회차별 위치·읽음 표시만 허용합니다. 서버에서 필드를 검사하므로 표지, 리더 설정, 소스 비밀번호는 이 API에 저장할 수 없습니다.
- 항목마다 버전을 비교해 갱신합니다. 오래된 수정은 현재 서버 값을 받아오며, 서로 다른 항목은 독립적으로 합칩니다. 삭제 상태를 남겨서 오래된 기기의 기록이 되살아나는 것을 막습니다. 한 요청의 용량 검사를 통과하지 못하면 그 요청 전체를 저장하지 않습니다.
- 기존 계정 저장소(Redis 또는 로컬 파일)에 계정당 5MiB·3,000항목까지 보관합니다. 별도 DB 서비스나 이미지 저장소는 추가하지 않았습니다.
- 큰 동기화 응답은 약 512KiB씩 나누어 받아 Vercel의 단일 응답 제한을 넘지 않습니다. 쓰기 응답은 해당 요청의 결과도 포함하며, 모든 조각을 받은 뒤 기기의 동기화 버전을 갱신합니다.
- 브라우저는 전송할 변경사항을 계정별 로컬 저장소에 먼저 기록합니다. 약 15초마다 묶어 보내고, 처음 접속하거나 앱으로 돌아오거나 연결이 복구될 때 받아옵니다. 실패 시 재시도 간격을 늘립니다.
- 첫 동기화 시 기존 로컬 기록 중 서버에 없는 항목만 올립니다. 다른 기기로부터 받은 변경으로 현재 읽고 있는 페이지를 강제로 이동시키지는 않습니다.
- 표지와 표지 주소는 보내지 않습니다. 다른 기기에서 이어 읽을 때 상세 정보를 다시 불러오고, 새 표지를 그 기기의 기존 캐시에 보관합니다.
- 동기화 한도에 도달하면 안내를 표시하고 변경사항을 기기에 유지합니다. 읽음 표시·삭제 상태도 항목 수에 포함되며, 서버 데이터를 자동으로 삭제해서 한도를 확보하지 않습니다.
- 후속 검증: 실제 Redis를 포함한 서버 테스트 44개, 두 브라우저의 계정 동기화(만화 페이지·소설 문단 위치·오프라인 재접속·삭제·표지 재수신), 로그인, PWA 검증 통과. 기존 탐색·최근 읽기·빠른 이동·소설 리더 회귀도 확인했습니다.

### CI 수정 및 동기화 한도 검증

- 소설 단축키 회귀 테스트는 설정창의 `open=false`나 최초 초점 복귀만 기다리지 않고 실제 `close` 이벤트 처리가 끝날 때까지 기다립니다. 기본 Chromium에서 설정창 닫기 후 초점이 두 번 복귀하던 경합을 제거했습니다.
- 같은 작품·회차를 200번 갱신해도 최근 읽기 1개와 위치 1개만 유지하며, 변경 전 위치의 이력은 저장하지 않습니다. 새 회차와 삭제 표시는 별도 항목으로 남습니다.
- 5MiB 미만의 4.5MB 초과 데이터를 파일 저장소와 실제 Redis에서 저장·분할 조회하고, 5MiB 초과 쓰기가 일부만 저장되지 않는지 검사합니다. 새 브라우저에서도 340개 회차 위치를 여러 응답으로 빠짐없이 받아오는 회귀 검증을 추가했습니다.
